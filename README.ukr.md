# Home Dashboard

Монорепозиторій для домашньої панелі керування, яку можна розмістити на власному сервері. Наявний застосунок Next.js розташований у `apps/web`.

## Структура репозиторію

- `apps/web` — застосунок Next.js App Router та інтерфейс.
- `apps/worker` — процес воркера; тут можна додавати заплановані задачі.
- `packages/database` — схема Prisma, міграції, клієнт і репозиторій користувачів.
- `packages/integrations` — спільний UDP-клієнт Marstek і перевірка відповідей.
- `docker` — Dockerfile сервісів.

Воркер опитує налаштовані акумулятори Marstek. Інші інтеграції з пристроями та зовнішніми API ще не реалізовані.

## Розробка

```bash
npm install
npm run dev
```

Відкрийте [http://localhost:3000](http://localhost:3000). Запускайте `npm run typecheck` для перевірки типів обох застосунків і `npm run lint` для вебзастосунку з кореня репозиторію.

Для локальної розробки телеметрії задайте `DATABASE_URL` і `MARSTEK_DEVICES` у `.env`, застосуйте міграції командою `npm run db:migrate` і запустіть `npm run dev:worker` в іншому терміналі. Найпростіше запустити PostgreSQL і весь стек через Docker Compose за інструкцією нижче.

## Docker Compose

Скопіюйте `.env.example` у `.env`. Задайте надійні різні значення для `POSTGRES_PASSWORD` і `AUTH_JWT_SECRET`. Згенеруйте секрет JWT командою `openssl rand -base64 48`. Для пароля PostgreSQL використовуйте символи, безпечні для URL (літери, цифри, `_` або `-`), оскільки Compose також вставляє його у `DATABASE_URL`. Для першого користувача задайте `INITIAL_USER_FIRST_NAME`, `INITIAL_USER_LAST_NAME`, `INITIAL_USER_LOGIN` і `INITIAL_USER_PASSWORD`. Пароль має містити 12–128 символів, а логін — 3–50 малих латинських літер, цифр, `.`, `_` або `-`.

Стек Compose підключається до наявної зовнішньої Docker-мережі `shared`; за потреби створіть її один раз командою `docker network create shared`. Вебсервіс публікує порт `WEB_PORT` на інтерфейсах хоста (типово 3000), щоб до нього могли підключатися інші локальні програми. PostgreSQL не публікується на порти хоста; він доступний у мережі Compose та в довіреній мережі `shared` за псевдонімом `home-dashboard_postgres`.

```bash
cp .env.example .env
docker compose build web worker
docker compose up -d
```

Compose чекає готовності PostgreSQL, застосовує міграції та автоматично запускає `setup` перед web і worker. Перший користувач створюється з `INITIAL_USER_*`, лише якщо таблиця користувачів порожня. За наявності користувачів початкове налаштування пропускається навіть після видалення початкових облікових даних. Паролі наявних користувачів не змінюються. Невалідні початкові дані блокують перший запуск із явною помилкою setup.

Для окремого env-файлу передавайте його в кожну команду Compose: `docker compose --env-file ~/Envs/HomeDashboard.env up --build --detach --remove-orphans`. Compose сам передає дані користувача та `DATABASE_URL` до setup. Для прямого локального запуску `npm run db:create-user` потрібно окремо задати `DATABASE_URL`.

Щоб додати ще одного користувача, задайте `INITIAL_USER_*` і виконайте `docker compose --env-file ~/Envs/HomeDashboard.env run --rm setup npm run db:create-user` (для локального `.env` параметр `--env-file` не потрібен). Явна команда вмикає ручне створення в уже налаштованій базі. Після використання приберіть `INITIAL_USER_PASSWORD` з env-файлу. Для застосування лише міграцій запускайте `docker compose run --rm migrate` з тим самим env-файлом.

Панель керування доступна за адресою [http://localhost:3000](http://localhost:3000) зі стандартним `WEB_PORT`. PostgreSQL не має порту на хості.

Користувачі панелі входять за створеними логіном і паролем. Вкладка **Мої сайти** містить посилання на Timeflow API, Timeflow, Portainer, Torrent, Plex, pgAdmin і Redis. Публічного маршруту реєстрації немає. Паролі зберігаються як хеші scrypt, а восьмигодинна сесія JWT — у cookie HttpOnly. Том `postgres_data` зберігає дані бази між перезапусками.

## Marstek Venus E 3.0

Увімкніть **Local API** у застосунку Marstek і дозвольте UDP-трафік від Docker-хоста до кожного акумулятора. У `.env.example` перший пристрій налаштований як `192.168.3.224:30000`. Інші пристрої додаються до JSON-масиву `MARSTEK_DEVICES` з унікальними сталими ID:

```dotenv
MARSTEK_DEVICES='[{"id":"venus-e3-1","name":"Living room","host":"192.168.3.224","port":30000},{"id":"venus-e3-2","name":"Garage","host":"192.168.3.225","port":30000}]'
```

Після зміни конфігурації або оновлення застосунку перебудуйте образи, застосуйте збережену міграцію і запустіть воркер:

```bash
docker compose build web worker
docker compose run --rm migrate
docker compose up -d
```

Воркер опитує кожен пристрій щосекунди та одразу після запуску, не допускаючи паралельних циклів. Якщо пристрій відповідає повільно або не відповідає, наступний цикл починається після завершення поточного. Повільні необов’язкові запити `Bat.GetStatus` і `ES.GetMode` виконуються раз на хвилину, а між ними використовуються останні отримані значення. Усі запити використовують адресний UDP; команд керування воркер не надсилає. Помилка необов’язкового запиту не скасовує коректні дані енергосистеми. Дашборд оновлюється через автентифікований WebSocket після збереження нового виміру; також діє періодичне оновлення як резервний варіант. Зберігайте сталі ID пристроїв, щоб історія лишалася прив’язаною до них після зміни назви чи IP. Видалені з конфігурації пристрої залишаються в БД з історією, але позначаються вимкненими.

Час вимірів зберігається в UTC; потужність — у Вт, температура — у °C, ємність та енергія — у Вт·год, SOC — у %. Енергія заряджання й розряджання оцінюється за сусідніми вимірами потужності; проміжки понад п’ять хвилин виключаються. Деякі прошивки не повертають `bat_power`; тоді дашборд оцінює потужність за сонячною, мережевою та резервною потужністю й показує джерело значення. Історія зберігається 90 днів. Доступні періоди 1 година, 6 годин, 24 години, 7 днів, 30 днів і власний діапазон дат до 90 днів; виміри агрегуються в інтервали по одній або десять хвилин. Також дашборд оцінює час до розрядження за поточною потужністю та залишковою ємністю. Вибраний пристрій позначається офлайн після трьох хвилин без виміру; сповіщення про недоступність підтверджується після трьох хвилин поспіль невдалих опитувань, а про відновлення — після 30 секунд успішних відповідей. Проміжки опитувань понад 30 секунд перезапускають підтвердження. Має працювати лише одна репліка воркера, бо захист від накладання запусків діє всередині процесу.

## Моніторинг Freelancehunt

Задайте `FREELANCEHUNT_API_TOKEN` у `.env`, щоб завантажити список навичок і дозволити воркеру опитувати Freelancehunt. Для сповіщень у Telegram додатково задайте `TELEGRAM_BOT_TOKEN` і `TELEGRAM_CHAT_ID`. Після застосування міграцій і запуску стеку відкрийте **Settings** у дашборді, щоб увімкнути моніторинг проєктів і непрочитаних повідомлень, вибрати навички для проєктів, налаштувати інтервал опитування (10–3600 секунд; за замовчуванням 60) та сповіщення Telegram. Вкладка Freelancehunt показує проєкти сторінками й відкриває повний опис у діалоговому вікні. Під час першого опитування поточні результати зберігаються як початковий стан; сповіщення надсилаються для нових знахідок надалі. Нові проєкти та непрочитані повідомлення також з’являються у сповіщеннях дашборду через автентифікований WebSocket.

Моніторинг і керування контейнерами виконуються окремо в Portainer. Панель не має доступу до Docker socket.

Проєкти Freelancehunt відбираються лише за фільтрами, без оцінок і порогів. Персональні сповіщення враховують збережені фільтри вмісту; Telegram — вибрані для збору навички, джерела та рівень важливості каналу. Збережені проєкти, нотатки й статуси перегляду залишаються персональними.
