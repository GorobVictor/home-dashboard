# Home Dashboard

Монорепозиторій для домашньої панелі керування, яку можна розмістити на власному сервері. Наявний застосунок Next.js розташований у `apps/web`.

## Структура репозиторію

- `apps/web` — застосунок Next.js App Router та інтерфейс.
- `apps/worker` — процес воркера; тут можна додавати заплановані задачі.
- `packages/database` — схема Prisma, міграції, клієнт і репозиторій користувачів.
- `packages/integrations` — спільний UDP-клієнт Marstek і перевірка відповідей.
- `docker` — Dockerfile сервісів і налаштування pgAdmin.

Воркер опитує налаштовані акумулятори Marstek. Інші інтеграції з пристроями та зовнішніми API ще не реалізовані.

## Розробка

```bash
npm install
npm run dev
```

Відкрийте [http://localhost:3000](http://localhost:3000). Запускайте `npm run typecheck` для перевірки типів обох застосунків і `npm run lint` для вебзастосунку з кореня репозиторію.

Для локальної розробки телеметрії задайте `DATABASE_URL` і `MARSTEK_DEVICES` у `.env`, застосуйте міграції командою `npm run db:migrate` і запустіть `npm run dev:worker` в іншому терміналі. Найпростіше запустити PostgreSQL і весь стек через Docker Compose за інструкцією нижче.

## Docker Compose

Скопіюйте `.env.example` у `.env`. Задайте надійні різні значення для `POSTGRES_PASSWORD`, `PGADMIN_DEFAULT_PASSWORD` і `AUTH_JWT_SECRET`. Згенеруйте секрет JWT командою `openssl rand -base64 48`. Для пароля PostgreSQL використовуйте символи, безпечні для URL (літери, цифри, `_` або `-`), оскільки Compose також вставляє його у `DATABASE_URL`. Для першого користувача задайте `INITIAL_USER_FIRST_NAME`, `INITIAL_USER_LAST_NAME`, `INITIAL_USER_LOGIN` і `INITIAL_USER_PASSWORD`. Пароль має містити 12–128 символів, а логін — 3–50 малих латинських літер, цифр, `.`, `_` або `-`.

```bash
cp .env.example .env
docker compose build web worker
docker compose run --rm setup
docker compose up -d
```

Команда `setup` окремим кроком застосовує збережені міграції та створює першого користувача. Вона не скидає пароль наявного користувача. Щоб додати ще одного користувача, задайте інші значення `INITIAL_USER_*` і знову виконайте `docker compose run --rm setup`. Після використання приберіть `INITIAL_USER_PASSWORD` із `.env`. Для наступних змін схеми без створення користувача запускайте `docker compose run --rm migrate`. Усередині контейнера з налаштованим `DATABASE_URL` міграцію виконує команда `npm run db:migrate`.

Панель керування доступна за адресою [http://localhost:3000](http://localhost:3000), а pgAdmin — за [http://localhost:5050](http://localhost:5050). Увійдіть у pgAdmin за допомогою `PGADMIN_DEFAULT_EMAIL` і `PGADMIN_DEFAULT_PASSWORD` із `.env`. Підключення Home Dashboard PostgreSQL імпортується з `docker/pgadmin/servers.json`; пароль бази даних береться зі згенерованого файлу pgpass. PostgreSQL не має порту на хості, а обидва вебінтерфейси доступні лише через localhost.

Користувачі панелі входять за попередньо створеними логіном і паролем. Публічного маршруту реєстрації немає. Паролі зберігаються як хеші scrypt, а восьмигодинна сесія JWT — у cookie HttpOnly. Томи `postgres_data` і `pgadmin_data` зберігають дані між перезапусками. pgAdmin імпортує описи серверів під час першого створення свого тому з даними.

## Marstek Venus E 3.0

Увімкніть **Local API** у застосунку Marstek і дозвольте UDP-трафік від Docker-хоста до кожного акумулятора. У `.env.example` перший пристрій налаштований як `192.168.3.224:30000`. Інші пристрої додаються до JSON-масиву `MARSTEK_DEVICES` з унікальними сталими ID:

```dotenv
MARSTEK_DEVICES='[{"id":"venus-e3-1","name":"Living room","host":"192.168.3.224","port":30000},{"id":"venus-e3-2","name":"Garage","host":"192.168.3.225","port":30000}]'
```

Після зміни конфігурації або оновлення застосунку перебудуйте образи, застосуйте збережену міграцію і запустіть воркер:

```bash
docker compose build web worker
docker compose run --rm migrate
docker compose up -d
```

Воркер опитує кожен пристрій щосекунди та одразу після запуску, не допускаючи паралельних циклів. Якщо пристрій відповідає повільно або не відповідає, наступний цикл починається після завершення поточного. Повільні необов’язкові запити `Bat.GetStatus` і `ES.GetMode` виконуються раз на хвилину, а між ними використовуються останні отримані значення. Усі запити використовують адресний UDP; команд керування воркер не надсилає. Помилка необов’язкового запиту не скасовує коректні дані енергосистеми. Дашборд оновлюється через автентифікований WebSocket після збереження нового виміру; також діє періодичне оновлення як резервний варіант. Зберігайте сталі ID пристроїв, щоб історія лишалася прив’язаною до них після зміни назви чи IP. Видалені з конфігурації пристрої залишаються в БД з історією, але позначаються вимкненими.

Час вимірів зберігається в UTC; потужність — у Вт, температура — у °C, ємність та енергія — у Вт·год, SOC — у %. Енергія заряджання й розряджання оцінюється за сусідніми вимірами потужності; проміжки понад п’ять хвилин виключаються. Деякі прошивки не повертають `bat_power`; тоді дашборд оцінює потужність за сонячною, мережевою та резервною потужністю й показує джерело значення. Історія зберігається 90 днів. Доступні періоди 1 година, 6 годин, 24 години, 7 днів, 30 днів і власний діапазон дат до 90 днів; виміри агрегуються в інтервали по одній або десять хвилин. Також дашборд оцінює час до розрядження за поточною потужністю та залишковою ємністю. Пристрій позначається офлайн після трьох хвилин без виміру. Має працювати лише одна репліка воркера, бо захист від накладання запусків діє всередині процесу.

## Моніторинг Freelancehunt

Задайте `FREELANCEHUNT_API_TOKEN` у `.env`, щоб завантажити список навичок і дозволити воркеру опитувати Freelancehunt. Для сповіщень у Telegram додатково задайте `TELEGRAM_BOT_TOKEN` і `TELEGRAM_CHAT_ID`. Після застосування міграцій і запуску стеку відкрийте **Settings** у дашборді, щоб увімкнути моніторинг проєктів і непрочитаних повідомлень, вибрати навички для проєктів, налаштувати інтервал опитування (10–3600 секунд; за замовчуванням 60) та сповіщення Telegram. Вкладка Freelancehunt показує проєкти сторінками й відкриває повний опис у діалоговому вікні. Під час першого опитування поточні результати зберігаються як початковий стан; сповіщення надсилаються для нових знахідок надалі. Нові проєкти та непрочитані повідомлення також з’являються у сповіщеннях дашборду через автентифікований WebSocket.
